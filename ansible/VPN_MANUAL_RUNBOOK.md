# AWS VPN Ansible 수동 실행·인계 절차

- 작성자: 이유빈
- 작성일: 2026-10-07
- 작성내용: 기존 개인 MFA 세션을 사용하는 VPN 서버 확인 절차 초안 (#16)

## 1. 현재 상태

코드 작성과 로컬 문법·구성 검사 단계입니다.
실제 AWS 접속·파일 전달·서버 설정의 성공을 검증한 문서가 아닙니다.

준비한 항목:
- 기존 Ansible 2.14.18과 사용자 전용 SDK 실행 환경
- Controller의 Session Manager 플러그인
- VPN EC2 확인용 Playbook과 접속 대상 예시
- 전용 S3 전달 버킷의 암호화·공개 차단·HTTPS 강제·1일 만료 선언
- Foundation 역할의 전용 버킷 설정 관리 권한

남은 항목:
- 실제 접속 조건과 실효 권한 확인
- SSM 접속·S3 파일 전달 시험
- WireGuard 설치 방법과 서버 설정
- 개인키 공급·복구·교체 절차와 실제 검증

## 2. 인증의 구분

| 작업 | 인증 방향 |
|---|---|
| Terraform Foundation 작업 | 기존 foundation 실행 역할의 임시 세션 |
| 담당자가 직접 Ansible 실행 | 기존 개인 IAM 사용자의 personal MFA 임시 세션 |

기존 사람 관리자 권한을 활용하는 수동 운영 방식입니다.
최소권한으로 제한된 전용 Ansible 역할이 구현된 것으로 표현하지 않습니다.
예약·무인 실행이 필요하면 별도 인증 방식을 검토합니다.

## 3. 실제 실행 전에 확인할 조건

- 대상 AWS 계정·서울 리전·VPN EC2 ID를 확인합니다.
- 전용 S3 전달 버킷이 실제 생성되고 보호 설정이 적용됐는지 확인합니다.
- EC2의 SSM Agent와 관리 상태, EC2·Controller의 S3 통신 조건을 확인합니다.
- 실행자의 SSM 접속 및 전용 S3 파일 전달 권한과 상위 제한을 확인합니다.
- 승인된 작업 범위·비용·팀 일정과 세션 잔여 시간을 확인합니다.
- Foundation Apply가 필요한 경우 #45의 RDS 가동 조건과 일정을 조율합니다.

위 조건을 확인하기 전에는 실제 접속 명령을 실행하지 않습니다.
새 인프라 생성은 Foundation 전체 변경 검토와 지정 실행 절차를 따릅니다.

## 4. 실제 접속 대상 목록 준비

예시는 ansible/inventories/vpn_aws.example.yml입니다.
실제 실행용 사본은 Git 밖의 접근 제한된 폴더에 보관합니다.

사본에서 교체할 값:
- ansible_host: 실제 생성된 VPN EC2 인스턴스 ID
- ansible_aws_ssm_bucket_name: 실제 생성된 전용 전달 버킷 이름

예시 문자열을 실제 값으로 교체했다고 접속 검증이 끝난 것은 아닙니다.
State·Data 백업 버킷을 전달용으로 지정하지 않습니다.
인증정보·MFA 코드·WireGuard 개인키를 목록에 넣지 않습니다.
실행자의 인증은 개인 MFA 임시 세션으로 공급합니다.

## 5. 승인 후 실제 실행 순서

1. Controller의 저장소에서 기존 세션 도구로 personal MFA 임시 세션을 준비합니다.
2. 실행 주체·계정·세션 모드·만료 시각을 확인합니다.
3. 실제 접속 대상 목록으로 문법 검사를 수행합니다.
4. 지정된 작업 창에서 vpn_aws_preflight.yml을 실행합니다.
5. 결과와 실패 원인을 기록하고, 성공·실패 모두 작업 후 세션을 정리합니다.

실행 도구는 scripts/vpn-ansible-playbook.sh를 사용합니다.
확인용 Playbook의 성공을 WireGuard 터널·DB 접속 성공으로 기록하지 않습니다.

세션 정리는 기존 tf-session.sh의 clear 기능을 사용합니다.
clear는 환경변수의 임시 인증정보를 해제하지만 기본 AWS 인증으로 돌아갈 수 있습니다.
작업 종료 후 같은 터미널에서 AWS 명령을 계속 실행하지 않습니다.
발급된 임시 세션 자체가 즉시 폐기됐다는 의미는 아닙니다.

## 6. S3 파일 정리와 기록 보관

플러그인이 정상 실행 후 전달 파일을 삭제합니다.
중단으로 남은 전달 파일은 S3의 1일 만료 규칙으로 정리합니다.
정확히 24시간 뒤 실제 삭제되는 것을 보장하지 않습니다.

백업·복구 원본·장기 보관 로그를 전달 버킷에 저장하지 않습니다.
하루 이상 같은 전달 파일을 사용하는 작업은 만료 조건을 다시 검토합니다.

필요한 실행 로그와 시험 결과는 비밀값을 제거한 후 별도로 보관하고
프로젝트의 Evidence 기록에 연결합니다.
인증정보·개인키·서명된 임시 URL 등 비밀값이 포함된 원본 로그를
Git·이슈·공유 문서에 그대로 올리지 않습니다.

## 8. WireGuard 키 보관·독립 복구 준비

보완일: 2026-10-08

### 확인한 시험 결과

실제 VPN 키 대신 비밀값이 아닌 시험 문장을 사용했다.
이유빈·정태훈 두 사람의 기존 age 공개키로 SOPS 암호화했다.
각자가 자신의 age 개인키로 같은 암호문을 복호화하고 원문 일치를 확인했다.
전달 전후 시험 암호문의 SHA-256도 일치했다.
개인키는 교환하지 않았다.

시험 암호문 SHA-256:
`371bf49c5a85603dab94024a1df85c855569326a39e0537194dbf823938996b5`

결과 기록:
https://github.com/seokpan/seokpan-hybrid-infra/issues/16#issuecomment-6051153781

이 시험은 Controller 내 두 계정의 복호화 확인이다.
실제 VPN 키 생성이나 Controller 밖 복구 시험을 완료한 것은 아니다.

### 보관 책임과 파일 구분

- VPN 키 주 보관자: 이유빈
- VPN 키 예비 보관자: 정태훈
- 온프렘 Gateway와 AWS VPN 서버의 WireGuard 키는 별도로 생성한다.
- VPN 키 암호문은 Valkey 파일과 분리한다.
- 각자의 age 개인키는 본인이 관리하며 서로 전달하지 않는다.
- 예비 보관자 지정은 AWS Apply 실행 책임을 변경하지 않는다.

### Controller 장애 대비

- [ ] Controller와 독립된 보관 매체와 접근 책임을 확정한다.
- [ ] 각자의 age 개인키 예비본을 별도 암호로 보호한다.
- [ ] 예비본을 여는 암호와 도구를 Controller 없이 사용할 수 있게 준비한다.
- [ ] 같은 age 개인키로만 그 개인키 예비본을 암호화하지 않는다.
- [ ] 시험 암호문을 독립 매체에 복사하고 해시 일치를 확인한다.
- [ ] 별도 환경에서 개인키 예비본을 복원해 시험 암호문을 연다.
- [ ] 원문 일치와 시험 후 임시 개인키 정리를 확인한다.
- [ ] 실제 VPN 키 생성 후 암호문 독립 사본을 갱신하고 복구를 확인한다.

두 계정에 파일이 있다는 이유로 독립 사본 완료를 표시하지 않는다.
같은 물리 장치의 다른 폴더는 그 장치의 고장까지 대비하지 못한다.
실제 보호 경로·개인키·암호는 공개 문서와 Git에 기록하지 않는다.

### 실제 WireGuard 키 생성·공급 준비

- [ ] 최종 키가 다른 보호 위치에 이미 보관돼 있는지 확인한다.
- [ ] 기존 Gateway 도구를 활용할 생성 위치와 보호 전달 방법을 정한다.
- [ ] 키 생성 절차는 기존 키를 덮어쓰지 않도록 준비한다.
- [ ] 생성한 키를 이유빈·정태훈 공개키로 SOPS 암호화한다.
- [ ] 두 보관자의 복호화와 공개키 대응을 확인한다.
- [ ] 암호문 독립 사본과 복구 결과를 확인한다.
- [ ] 해당 서버에 필요한 개인키만 공급하는 절차를 준비한다.
- [ ] 전송 경로와 임시 평문·S3 잔류 가능성을 검토한다.
- [ ] 임시 자료를 정리하고 키 공급·복구·교체 결과를 기록한다.

Ansible의 no_log만으로 비밀값의 안전한 공급이 완료됐다고 판단하지 않는다.
WireGuard 개인키와 age 개인키를 Terraform user_data·Plan·State·Output에 넣지 않는다.

현재 상태: 절차 준비. 실제 VPN 키 생성·서버 공급·독립 복구는 미실행.

실제 WireGuard 개인키 생성·암호화 보관·터널 복구는 아직 미실행이다.
AWS 접속·Terraform Plan·Apply도 이번 검사에서 실행하지 않았다.

## 다른 PC의 USB 예비본 복구 시험 — 2026-10-08

### 수행 결과

- 대상: Controller와 다른 물리 PC의 worker-01.
- 실행 방식: 기존 Controller에서 SSH로 접속하여 worker에서 복호화.
- USB 시험 암호문의 SHA-256이 기존 기록과 일치함.
- USB의 암호화된 주 보관자 age 개인키 예비본을 비밀번호로 복호화함.
- 복구한 개인키에서 추출한 공개키가 기존 기록과 일치함.
- 복구한 개인키로 USB 시험 암호문을 복호화하고 원문 일치를 확인함.
- Controller의 기존 개인키 파일을 worker에 복사하지 않음.
- 임시 복구 개인키·시험 평문은 시험 종료 시 삭제됨.
- worker의 임시 도구·시험 실행 파일 정리 완료.
- USB 예비본과 Controller의 기존 개인키는 유지함.
- 패키지 설치·서비스 설정 변경·실제 VPN 키 생성·AWS 접속은 미실행.

### 검증 범위

다른 물리 PC에서 USB 예비본으로 기존 age 개인키를 복구하고
시험 암호문을 여는 데 성공함.

Controller는 SSH 접속에 사용했으므로, Controller를 사용할 수 없는
상황의 전체 복구 절차를 검증한 것은 아님.

### 남은 작업과 미검증 항목

- 실제 WireGuard 키 생성.
- 실제 WireGuard 개인키의 암호화 보관.
- 실제 WireGuard 개인키의 복구 및 공개키 일치 시험.
- Controller를 사용할 수 없는 상황에서 다른 접속 수단으로 수행하는 복구 시험.
- 실제 VPN 서버 설정 및 터널 연결 검증.

### USB 상태

- worker-01에서 sync 실행 및 USB 마운트 해제 완료.
- VMware에서 USB 연결 해제 완료.
- Windows에서 안전하게 꺼내기 완료.
- USB 물리적 분리 및 회수 완료.
- USB의 암호화된 개인키 예비본과 시험 암호문은 유지함.

이전 Controller에서 안전한 제거 절차 없이 분리한 이력이 있으나,
이후 다른 PC에서 시험 암호문의 해시 일치와 개인키 예비본 복호화,
시험 암호문 복호화·원문 일치를 확인함.
이 결과는 해당 파일의 검증이며 USB 전체 파일이나 파일시스템의
무결성 검사를 완료했다는 의미는 아님.

## 실제 온프렘 VPN 키 암호화·주 보관자 검증 — 2026-10-08

### 완료한 작업

- 온프렘 Gateway의 기존 WireGuard 도구로 실제 개인키·공개키를 생성했다.
- 두 보관자의 기존 age 공개키를 사용해 SOPS로 개인키를 암호화했다.
- 암호문은 Controller의 Git 밖 보호 폴더에 저장했다.
- 주 보관자의 기존 age 개인키로 실제 암호문 복호화에 성공했다.
- 복구한 WireGuard 개인키에서 계산한 공개키가 보관한 공개키와 일치했다.
- Ansible 복호화 설정을 수정한 뒤 기존 암호문의 복호화를 재검사했다.
- Ansible 검사 결과: ok=2, changed=0, unreachable=0, failed=0.
- 재검사에서 키 재생성이나 기존 암호문 재작성은 하지 않았다.
- 임시 검사 파일과 임시 로그는 정리했다.

### 실패 원인과 수정

기존 복호화 작업에 SOPS_AGE_KEY_CMD를 빈 문자열로 설정했다.
이는 해당 환경변수를 제거하는 것과 다르며, 빈 명령 실행 문제를 일으켰다.

복호화 명령 실행 시 SOPS_AGE_KEY와 SOPS_AGE_KEY_CMD를 제거하고,
SOPS_AGE_KEY_FILE로 기존 개인키 파일을 지정하도록 수정했다.
수정 후 Ansible 복호화 검사는 통과했다.
